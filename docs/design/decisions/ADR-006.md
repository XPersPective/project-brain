# ADR-006 — Unattended session setup and Baton Relay

## Status

Accepted, 2026-11-05. Extends ADR-005 and the 3.9 Baton Relay Policy (BRP) for
hours/days of unattended, circulating directors. Cross-repository contract:
[director-contract.md](../../../skills/project-brain/references/director-contract.md).

## Problem (observed)

A relay from a Claude host director to Antigravity via CLI Agent Pool (CAP)
failed four times on native permissions (compound/multi-line shell, MCP calls,
reading the skill outside the workspace) because two Antigravity projects mapped
one folder. Each failure left the relay `ACTIVE` with a dead director or
`HANDOFF_PENDING` forever, and failed write tasks left `needs_review` workspace
locks. A successor could not prove it inherited the launcher's confirmation, and
the env-only baton token did not survive shells that drop environment changes.

## Decision

### A. One batched setup question, defaults after 5 minutes

User-facing setup uses Turkish conceptual names: Çalışan seçimi (ESP), Çalışma
düzeni (SP), Kota yenilenmesini bekleme (QRP), Yönetici devri (BRP), and Yeni
yöneticinin seviyesi. Questions explain the behavior without requiring acronyms;
English policy keys, exact provider/category identifiers and machine statuses stay
unchanged. The compact opening states the tool-first economy rule and retains
verification/review. The displayed defaults and five-minute confirmation flow
remain the existing authority contract.

- `PB setup ask` prints one numbered, plain-language batch with the default under
  each question and records `asked_at`: 1 execution source (ESP) and worker tier,
  2 scheduling (serial/parallel + max workers), 3 QRP, 4 BRP (on/off, threshold),
  5 director tier (CAP category, same as the launcher, or exact routes).
- Defaults are the saved policy only when its bytes equal the last confirmed
  policy (an edited, never-confirmed file cannot become a default); otherwise
  Solo / Serial 1 / QRP off / BRP off / same director tier.
- Explicit answers: `PB policy --file … --confirm` (unchanged).
- No answer: `PB setup wait` sleeps at most 60 s per call (the host delivers a
  user reply between calls) until 5 minutes after `asked_at`; `PB setup defaults`
  then saves and confirms the shown defaults with note "defaults after timeout".
  Before the timeout it needs `--accepted` (the user said "use defaults").
- The relay baton holder gets `RELAY_SUCCESSOR` from `setup ask`; any other
  session sees that a relay owns the project. Pool workers are never asked.

### B. Director and worker tiers

- Worker tier stays ESP (`cap-category` categories, `cap-pinned`, or native host
  models). Director tier is `relay.director_category`: a CAP category id or
  `same` (the default when no explicit `relay.candidates` are listed), meaning
  the categories that contain the launcher's route/model. Unresolvable `same`
  fails loudly. Categories resolve to concrete `{route, model, effort}` at
  `relay start` and when a confirmed policy edit is adopted (D); successors use
  the frozen list and never re-resolve or re-ask.

### C. Inheritance and authority

- The relay record holds the hash and a copy (`inherited`) of the whole
  normalized executor policy. The live baton holder counts as confirmed; it
  never rotates the session nonce or session modes (`boot --new-session` prints
  `RELAY_SUCCESSOR: settings inherited; ask no setup questions`).
- Authority = the baton token, from env `PB_RELAY_TOKEN` or the global
  `--relay-token` argument (works in shells that drop environment changes). With
  CAP `secretEnv` the token is injected into the successor's process environment
  and is neither stored by CAP nor written into the prompt (prompts are readable
  through CAP).

### D. Policy edits mid-relay (one adoption point)

`_adopt` runs under the checkout lock inside `assess`, `handoff`, `takeover` and
`recover`. If the policy file differs from the record and the user confirmed it
(a confirmation receipt matches the file bytes), the record adopts it
(`POLICY_ADOPTED`) and re-resolves candidates; a disabled relay becomes
`STOPPED` and its pending successor is cancelled. An unconfirmed edit is ignored:
the holder works under `inherited` and boot warns. Takeover never fails because
of a policy change, so an edit cannot strand a handoff.

### E. Readiness before trust

- Readiness = CAP `pool_preflight` for the director capabilities (multi-line and
  compound shell, CAP MCP, reading the installed skill outside the workspace, Git
  commit and remote, local CAP service), verified by CAP itself (HMAC probe files,
  native tool events, random-line native read, MCP ack, loopback POST, object
  write, `ls-remote`) and cached under a settings-hash key. The skill version is
  checked again at takeover.
- `relay start` resolves candidates, preflights each and prints a table; it
  refuses when none is ready and otherwise starts with the ready ones, listing
  the failed. Without CAP `preflight` it refuses unless `--unverified`, shown as
  "readiness: unverified" in status. It also prints which unattended guarantees
  CAP provides (watchdog requires the CAP service running).
- Health per candidate `{status, checked_at, failures, reason}`. A preflight takes
  the workspace lock, so a planned handoff (live director holds the lock) reads only
  `pool_preflight_status` and skips candidates without a current ready result;
  recovery after a dead director (lock released) runs fresh probes.

### F. Two-phase handoff and failover

- `relay handoff --task --next` (candidate optional) reads quotas through CAP
  itself, selects the next ready candidate above the threshold (quota-unknown
  candidates only when none is known above it), preflights, checkpoints and
  submits with `onExit`, `ackDeadlineSeconds`, `startDeadlineSeconds`,
  `idleTimeoutSeconds` (CAP hang detection) and `secretEnv` when available. The old director remains the record's
  holder until the successor's `relay takeover` (which acks its CAP task). It
  stops at once and ends its CAP task with a `completed` report "handed off", so
  CAP does not lock the workspace.
- `relay recover` is the single idempotent reconciler (checkout lock up to 90 s,
  generation/pending-checked, acting only on observed CAP states). It runs from
  the CAP `onExit` hook of every director task, from `relay start`, and manually;
  `boot` and `relay status` stay read-only and only report.
  - Pending successor terminal without takeover, or running past
    `takeover_minutes` (default 15) → cancel if needed, mark unhealthy, next
    candidate, new token (`FAILOVER`). Queued behind the handed-off director still
    running after the start deadline → cancel that director (it already handed
    off), keep the candidate.
  - Pending successor queued behind a lock the relay does not own → `EXHAUSTED`
    with a notice (the user's or another task's review blocks the workspace).
  - Pending with no CAP task id (lost response) → find it by its label via
    `pool_list_tasks`; if absent, failover. Active director-labelled tasks that
    are neither holder nor pending are cancelled (late duplicates).
  - Holder is a CAP task that ended without a handoff (crash, timeout, quota) →
    start the next candidate from the last checkpoint (`RECOVER`; newest handoff
    record, else task Resume; the successor classifies the dirty tree).
  - Relay-owned `needs_review` tasks (director tasks, workers linked to them via
    `parentTaskId`) →
    `pool_resolve_task` when available, else the exact `cli-agent-pool resolve`
    instruction.
- Loop bounds: a candidate is unhealthy on permission/auth/readiness/version
  failure, or after two failures; failures reset only after progress (`assess`,
  `handoff`, `complete` by that director). Three consecutive unplanned transfers
  without progress → `EXHAUSTED`. `max_handoffs` caps planned handoffs (durable
  counter; history keeps 200 rows).
- `EXHAUSTED` is the only user notification: boot line, status, and one
  `CAP_NOTIFY` line printed by the next hook/recover until announced. It is not
  retried automatically when quotas renew; the user restarts with `relay start`.

### G. Other failure modes

- Duplicate directors: single holder, generation/pending checks, token rotation,
  late-duplicate cancellation, takeover cancels a still-running previous CAP
  director. A live record whose holder is a terminal CAP task and has no live
  pending is reset by `relay start` (`STALE_RESET`) instead of `RELAY_ACTIVE`; a
  host-only holder still needs `relay stop`, because its death is unobservable.
- The host launcher is not watched and cannot be cancelled by takeover. A user
  who leaves should have it hand off at once (`relay handoff` works at any quota).
- Skill version: the record keeps `skill_version` and the absolute `brain.py`;
  takeover refuses a lower running version (`RELAY_SKILL_OLD`) and records a
  higher one. Live schema-1 records (3.9) are upgraded in place on first write,
  keeping the holder's token and recognizing the 3.9 relay-only policy hash.
- Unknown holder quota: `assess` says UNKNOWN and work continues; provider
  exhaustion ends the CAP task and recover takes over.
- No host alarms, cron or Python scheduler are installed.

## Consequences

A director's protocol is: `relay assess` at checkpoints; on `HANDOFF_REQUIRED`
one `relay handoff --task --next`, then a `completed` report and stop; `relay
complete` at the end. Everything else is the reconciler's job. Unattended
guarantees depend on the CAP features present and are printed, not assumed.

## Critique log

Round 1 (self): handoff counter lost after 200 history rows → durable counter;
boot must not submit → recover only from hook/start/manual; recovery without a
handoff checkpoint → Resume fallback, hash check only when present; re-preflight
cost → only when older than 60 min; EXHAUSTED not auto-retried → stated.

Round 2 (independent reviewer, 12 findings), all adopted:
1. Normal handoff ended `needs_review` (incomplete report) and locked the
   workspace → `completed` "handed off" report; `releaseLockOnFailure` covers
   WORK_INCOMPLETE/INVALID_REPORT/interruption.
2. Queued successor had no timer → `startDeadlineSeconds`; foreign blocker →
   EXHAUSTED notice; blocking handed-off director → cancelled.
3. Lost submit response → label lookup via `pool_list_tasks`; stray director
   tasks cancelled.
4. Task id spoofable, token readable in prompt → per-task secret returned only
   to the submitter; no token in prompt (superseded in round 4 by `secretEnv`).
5. Endless failover → failures reset only after progress; 3 unplanned transfers
   without progress → EXHAUSTED; `max_handoffs` counts planned handoffs.
6. Adoption contradictions → single `_adopt` under lock in assess/handoff/
   takeover/recover, re-resolving candidates; disabled → STOPPED + cancel.
7. Hook lock contention, CAP restart → recover waits up to 90 s; startup
   interruption follows `releaseLockOnFailure`; watchdog-needs-CAP printed.
8. Live record upgrade → in-place upgrade keeping 3.9 token and hash semantics.
9. Probe side effects → `git … -h`, `ls-remote` with prompts disabled from PB,
   `relay probe` allowed while live.
10. Setup defaults from an edited file → only a previously confirmed file is a
    default; non-holders are not asked while a relay is live.
11. Host launcher → hand off at once when leaving; `same` fails loudly.
12. Lost exhaustion notice → announced flag; printed until announced.
Simplification: removed the write-probe fallback and the 24 h freshness window.

Round 3 (independent reviewer, second pass, 6 findings), all adopted: secret
race on a host launcher's first handoff and secret loss on a lost response (both
removed by `secretEnv`: PB generates the token, so its hash exists before submit);
delegated workers misread as foreign locks (relay owns linked tasks;
only a foreign `needs_review` blocker exhausts); START_TIMEOUT
counted twice (no penalty, handed-off blocker cancelled); adoption needs a
nonce-free receipt check and a durable "last confirmed" record; 3.9 upgrade copies
the policy only when its relay block matches the 3.9 hash, else STOPPED.

Round 4 (cross-repository reconciliation with the CAP session): CAP had designed
its own relay table and watchdog. Two relay brains could start duplicate
directors, so CAP keeps mechanisms only and Project Brain keeps the relay. Adopted
from CAP's design: CAP-verified, cached, lock-taking preflight with a lock-free
status read (replaces PB's own probe receipts and a lock-free probe), fingerprint
lock release, project-ambiguity failure, linked workers, idle-hang detection.

Round 5 (self): no material gaps found. Residual limits: host
director death is unobservable; the watchdog stops when the CAP service is not
running; EXHAUSTED needs the user.

Round 6 (continuation self-review): creation time cannot establish lock ownership;
only recorded directors and linked workers may be resolved. A pending task found
by label after a lost submit acknowledgement must be excluded from stray
cancellation. Confirmation reads the actual policy file even while the baton
holder uses inherited settings. Fast takeover uses CAP's task-id environment
before submit returns. Director submissions explicitly request the advertised
`directorProfile` with the same read paths as preflight. Regression checks cover
these changes.

CAP's scoped director lease permits successor submission and self-acknowledgement;
ordinary worker leases cannot create directors. PB's RPC environment retains this
lease and the worker marker, while provider secrets remain filtered. Owner-only
preflight and lock resolution run from the launcher or service exit hook.
