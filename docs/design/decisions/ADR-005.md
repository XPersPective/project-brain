# ADR-005 — Enforced executor, scheduling and quota recovery choices

## Status

Accepted, 2026-11-01. Implements the user's ESP/SP/QRP and publication request.

## Decision

- Parse the durable executor-policy.json instead of treating it as prose. Bind
  execution/review, exact native/CAP identities, categories and supported effort;
  SP remains an independent concurrency limit. New-session confirmation is a
  local declared receipt bound to policy bytes and the session nonce, not identity
  authentication. Changing policy invalidates that receipt. Readback of existing
  jobs remains possible; changed choices govern new dispatch only.
- Use CAP's installed skill/procedure and compact metadata. Category IDs are
  opaque; catalog pins do not acquire a forced category. Category names/cost are
  not capability evidence. Preserve existing risk/review independence and source
  evidence. Unknown host identity/cost cannot prove a pinned/cheapest restriction.
- QRP is opt-in and director-only. Record enabled/disabled and a user-selected
  low-quota threshold (suggest 10%). Never infer remaining reasoning/context
  tokens from provider quota; unknown readings stay unknown.
- Before exhaustion, save actual task Resume/handoff and prepare one durable wake
  intent. The host creates/updates a same-thread automation through its own tool;
  Python does not install a hidden scheduler. Bind wake to account hash, policy,
  checkpoint and nonce; on callback verify current account, quota reset, policy
  and cancellation before permitting continuation. Account switch, stale policy,
  uncertain automation creation or cancellation refuses automatic work.
- Auto-wake may reuse the explicitly opted-in saved ESP/SP only after these checks;
  ordinary new interactive sessions still confirm ESP/SP/QRP. Cancel revokes wake
  authority even if host deletion fails. Never redeem paid/reset credits, switch
  accounts, mutate worker jobs or promise uninterrupted execution on unsupported
  hosts. Host/account metadata may be private; publish only symbolic references.

## Work and verification

1. Isolated policy module and tests; seven ESP sources, session receipts, bounds.
2. Isolated QRP module and tests; account/reset/checkpoint/cancel/idempotency guards.
3. Integrate boot/CLI, CAP/direct/native dispatch and serial drain; no bypass via
   old modes or environment overrides. Add meaningful integration regressions.
4. Verify actual host usage/automation capabilities and current CAP metadata only;
   provider work is unnecessary for metadata validation. Independent review,
   Python 3.8/3.11 offline suites, index-built reproducible release and GitHub
   publication with the existing human identity. Refresh managed installations.

## Limits

Local records are declarations, not an OS sandbox or authenticated identity.
Host tools must expose stable account/quota/scheduling observations. A machine
that is asleep/offline or a host that cannot wake the same chat cannot guarantee
continuous coding. Fail closed and retain recoverable state rather than replay.

## Implemented validation

3.8.0 implements the modules, CLI and shared-dispatch guards above. Full offline
regressions passed on Windows Python 3.8.20 and 3.11.15. Scoped independent review
found three authority gaps (default effort, response work during QRP wait and
cancellation approving pending policy); fixed and covered by regressions.
Current CAP metadata and a paused host heartbeat create/delete were observed.
The release-session alarm is cancelled; no active test timer remains. These
observations do not certify arbitrary provider execution or uninterrupted uptime.
