# ADR-007 — Seven-item Turkish setup, Bağımsız İkinci Görüş, Turbo and graceful relay stop

## Status

Accepted, 2026-11-05. Extends ADR-005 and ADR-006 for Project Brain 3.11.0.

## Context

The 3.10.0 setup asked five questions with conservative solo/serial/disabled defaults
and no single-page interactive widget, no mixed native+CAP worker source, no explicit
balanced/turbo speed dimension, no graceful 2-minute relay stop, and no unified
opening screen when a background quota-recovery wait owned the project. In addition,
the user finalized the role and **Bağımsız İkinci Görüş** rules in
`docs/design/PROTOCOL-DISCUSSION.md`.

## Decision

Implementation tasks (2026-11-05): wire durable `setup clarify --answer` with
a fresh 300-second deadline and optional resolved policy file; block dispatch
while details are pending; retain resolved answers on timeout. Add explicit
`cap_fallback: native|wait`, role-aware `setup recover-cap --role` authorization
and mandatory notification. Never replay uncertain CAP jobs. Verify through CLI
regressions, full offline suite, rendered form checks and independent review.
Keep existing GC recovery guards; bound context reads rather than deleting chat
history or unfinished evidence. Source development tracking remains retired.

Distribution follow-through: verify installed CAP 2.2.0 compact metadata and
pb-director/1 through isolated real-daemon integrations; refresh obsolete test
assertions without weakening execution/replay checks. Recheck automatic legacy
startup backups/idempotency, package reviewed index bytes, and update existing
Skills Manager deployments from this local source. Do not batch-migrate user
projects or install a login service: new-session orient/boot uses the refreshed
runtime and upgrades each project safely when opened.

### 1. Seven-item Turkish setup screen and inline HTML widget

`PB setup ask` presents seven items with vertical `✅` / `⬜` options and writes a
pre-filled single-page HTML card to `.project-brain/.cache/setup-form.html` from
`skills/project-brain/assets/setup-form.html` (zero per-session HTML generation tokens):

1. **Çalışma düzeni:** `✅ Paralel` (automatic ceiling up to host/quota capacity unless
   the user names a number) / `⬜ Sıralı`.
2. **Ajan kullanımı:** `✅ Çoklu ajan` / `⬜ Sadece yönetici` (`solo`; parallel tool
   calls remain allowed).
3. **Ajan kaynağı:** `✅ Yerleşik ajanlar` (`native`) / `⬜ Yerleşik ajanlar + CLI Ajan Havuzu`
   (`mixed`, optionally bounded by `categories`) / `⬜ Yalnız CLI Ajan Havuzu`
   (`cap-catalog`) / `⬜ Kullanıcı seçimi` (`native-pinned`, `cap-category`, `cap-pinned`).
4. **Çalışma hızı:** `✅ Dengeli: yüksek kalite, düşük toplam maliyet` (`balanced`) /
   `⬜ Turbo: sınırları zorlar, en hızlı bitirir` (`turbo`).
5. **Kota yenilenmesini bekleme:** `✅ Açık, %10` / `⬜ Kapalı`.
6. **Yönetici devri:** `✅ Açık, %10` / `⬜ Kapalı`.
7. **Devralacak yönetici:** `✅ Aynı havuzdan eşdeğer aday` (`director_category: "same"`) /
   `⬜ Kullanıcı seçimi` (explicit CAP category or `candidates`).

If the user selects `Kullanıcı seçimi` (or a pool option requiring details) without
naming the pool/category/model/account (`needs_clarification`), the director asks one
batched follow-up through `setup clarify --answer ... --file ...`; the file preserves
resolved answers and the runtime blocks dispatch until resolution. If no reply
arrives within a fresh 5 minutes (`setup wait` -> `setup defaults`), only missing
fields use the shown defaults. Repeated prompts do not restart the deadline. Explicit
`policy --file --confirm` resolves the pending state. HTML copies text; the user
sends it in chat and the host runs the timer loop, not the browser.

### 2. CLI Agent Pool unavailability (`cap_unavailable`)

- When `origin == "defaults"` without a preserved `cap_fallback: "wait"` restriction,
  `cap_fallback == "native"`, or `source == "mixed"`,
  and CLI Agent Pool is unreachable or has no eligible models, execution continues
  with host native agents (`CONTINUE_NATIVE`) and informs the user.
- When `origin == "user"` and the user explicitly selected a CAP-only source
  (`cap-catalog`, `cap-category`, `cap-pinned`), worker dispatch pauses (`WAIT`) and
  notifies the user without silently switching to native agents.
- Saved explicit CAP-only restrictions survive later session timeouts. Recovery is
  role-specific (`setup recover-cap --role exec|rev`), changes only the previously
  authorized role, and must relay its notification before new work. An active baton
  holder may recover; ordinary workers and stopping holders may not. Unknown CAP
  submissions require readback, never blind replacement.
- Director transfer (BRP) always requires CAP; when CAP is unavailable at the quota
  threshold, the director falls back to the quota-wait (QRP) rule.

### 3. Unified quota-wait (QRP) and director-transfer (BRP) threshold

- **Preparation at `threshold + 5%` (default 15%):** both `relay assess` and
  `quota assess` set `prepare_checkpoint: true` when remaining quota is within 5
  percentage points above the active threshold, so the director records `Resume` and
  checkpoint state before exhaustion.
- **Single trigger at `threshold` (default 10%):** when `relay.enabled` is true,
  `relay.threshold_percent` governs both BRP and QRP fallback. At 10%, the director
  stops starting new work:
  1. If BRP is enabled and a ready candidate has quota, hand off immediately without
     waiting.
  2. If no candidate is ready/available and QRP is enabled, enter same-account quota
     wait at the recorded checkpoint.
  3. If both are disabled or unavailable, save state, stop, and report the reason.
- The remaining 10% quota is preserved as a safety reserve for handoff verification
  and recovery.

### 4. Background relay and quota-wait opening screens + 2-minute graceful stop

- When `PB setup ask` runs while a relay is `ACTIVE`, `HANDOFF_PENDING`, `STOPPING`
  or `EXHAUSTED`, or while QRP is `PREPARED` or `ARMED`, it does not ask the 7 setup
  items. It shows the active holder/wait status and three Turkish choices (1: continue
  in background [default after 5 minutes], 2: stop/cancel, 3: stop/cancel and take
  over in this session).
- `PB relay stop` (`request_stop`) transitions a live relay to `STOPPING` with a
  120-second deadline (`stop_deadline`) and cancels any unconfirmed pending successor.
  The live baton holder sees `STOP_REQUESTED` on `relay assess` or any implementation
  gate (`RELAY_STOP_REQUESTED`), saves `Resume`/checkpoint, and calls `PB relay complete`
  (recorded as `STOP_ACK` -> `STOPPED`). If the holder does not withdraw within 120
  seconds (or with `--force`), `relay stop` / `relay recover` cancels the CAP task
  and releases relay-owned locks.

### 5. Non-negotiable roles, low-tier discovery and Bağımsız İkinci Görüş

- **Boot and discovery economy:** orientation (`orient`, `map`, `boot`) uses
  deterministic tools first, then the cheapest suitable allowed worker (`L` tier /
  low effort, ≤5 entrypoints, ≤150 words). Committed closed task evidence and unreferenced
  run logs are pruned automatically on `boot` (`gc_brain`), keeping context bounded.
- **Roles:** **Yönetici** (architecture, planning, decomposition, model/effort choice,
  final acceptance; may execute small/high-handoff-overhead tasks directly),
  **Uygulayıcı** (implements, runs tests, fixes own errors, delivers proof; never
  counts as its own independent reviewer), **Denetleyici** (on-demand independent
  verification for MEDIUM/HIGH risk or complex changes; starts one tier below the
  worker when capable, or equal/stronger when risk or failure requires).
- **Bağımsız İkinci Görüş:** required for initial architecture/roadmap planning and
  critical decisions (or steps the user marks critical). At least **one** additional
  independent opinion is obtained before locking the decision, in preference order:
  (1) equivalent different model, (2) one tier higher model for a narrow prompt,
  (3) one tier lower model with high effort, (4) same model in a clean separate
  session. The advisor receives only goal, requirements, constraints and facts — never
  the director's preferred answer. Advisory opinion does not replace post-implementation
  review (`Denetleyici`).
- **Balanced vs Turbo:** `balanced` optimizes quality, speed and total completion cost
  together; `turbo` pushes useful parallelism to the capacity ceiling and allows stronger
  models/higher effort when that shortens critical-path wall time, while preserving all
  quality, proof, review and **Bağımsız İkinci Görüş** floors.
